White paper · bil v0.6.0 · October 2026

Bounded Invariant Logic in Practice

Proving the safety logic of fourteen industrial, medical and security designs before they run, with every requirement traced to a qualified source.

bil projectModels: examples/domains/Sources: docs/whitepaper/CITATIONS.md

Abstract

Accident and recall investigations keep finding the same class of defect: interlocks, alarms and protocol state machines whose logic was wrong in the design, long before any code ran. bil (Bounded Invariant Logic) is a statically typed language that puts domain ontologies, first-order specifications, Dijkstra's guarded commands and reactive state machines in one source file, and checks them with weakest-precondition proofs, SMT solving and explicit-state model checking. The same file then runs on an interpreter, a bytecode VM or as a native binary.

This paper applies bil to fourteen domains, from semiconductor anneal control after spectroscopic ellipsometry to surgical teleoperation, process safety instrumented systems and TLS-style handshakes. Each model encodes requirements taken from standards, regulator reports and peer-reviewed physics, and each source is graded and cited. Across the suite, z3 proves all [[total:proved]] verification obligations with none left to sampling, the model checker explores [[total:states]] states in [[total:systems]] systems and proves [[total:ltl]] liveness properties, and all three execution back ends print identical results. Ten one-line seeded bugs, each modeled on a documented failure mode, are all caught with a concrete counterexample. The research also corrected four of our own first drafts, which is the strongest argument in the paper for tying formal models to primary sources.

1Why designs fail

The failures that matter most in safety-critical systems are rarely arithmetic slips. They are logic errors in how a system reacts to events: an alarm that does not latch, a state machine that accepts a message out of order, an interlock that is correct for each fault alone but not for two faults together.

  • Medical devices. Between 2005 and 2009 the FDA received about 56,000 adverse-event reports for infusion pumps and oversaw 87 recalls, 14 of them Class I. Its analysis traced many problems to design and engineering, including software defects such as failures of built-in safety alarms [[c:fda_ipii]].
  • Process plants. The U.S. Chemical Safety Board found that the 2007 T2 Laboratories explosion, which killed four employees and injured 28 people at nearby businesses, was a runaway reaction that most likely followed an inadequate reactor cooling system [[c:csb_t2]].
  • Security protocols. Systematic testing of TLS libraries found state-machine bugs that had gone unnoticed for years, including SKIP-TLS and FREAK, where a network attacker could skip handshake messages. The authors trace them to incorrect compositions of individually correct state machines [[c:beurdouche2015,ncc_smack]].

Industry has shown that this class of error can be found before deployment. Amazon Web Services has model-checked the designs of critical systems since 2011 and reports finding subtle bugs that testing missed [[c:newcombe2015]]. Tools such as SPIN [[c:holzmann1997]], which made model checking of protocols like Peterson's mutual exclusion [[c:peterson1981]] routine, TLA+, Alloy and Verus [[c:lattuada2023]] are mature. The barrier is that the domain model, the specification, the protocol model and the executable logic usually live in different tools and drift apart.

2The language and toolchain

bil keeps all four in one file. A program can contain:

  • Ontology: concept hierarchies with <: subtyping, algebraic data types, and first-order axioms over them.
  • Specified functions: fn with requires and ensures, written in Dijkstra's guarded command language [[c:dijkstra1975]]: if … fi with nondeterministic choice among enabled guards, and do … od loops with an invariant and a variant.
  • Reactive systems: system blocks with typed state, safety invariants, temporal properties (P ~> Q, eventually), an optional terminal condition and interleaved guarded transitions in the style of SPIN/Promela.
  • Data pipelines: |> chains of where, map, sort_by, sum and quantifiers over concrete data.

Verification conditions

For if G₁ → S₁ [] … [] Gₙ → Sₙ fi, bil verify generates guard totality (some guard holds under the precondition) and one obligation per branch, Gᵢ ⇒ wp(Sᵢ, Q). Because the semantics is demonic, a design with overlapping guards must be correct whichever enabled branch runs. For a do … od loop it generates five obligations: invariant initialization, preservation by every branch, non-negativity and strict decrease of the variant, and the postcondition on exit. The formal rules are in docs/SEMANTICS.md.

Each obligation ends in one of three verdicts:

  • PROVED (by z3): the SMT solver [[c:demoura2008]] showed the negated condition unsatisfiable.
  • REFUTED: a counterexample, with concrete values recovered from the solver's model, for example { x = 37 }.
  • BOUNDED (n samples): only sampled. bil verify exits with status 1 in that case unless --allow-bounded is given, so sampled evidence is never mistaken for a proof.

Model checking

bil model-check explores every reachable state of a system breadth-first, so each counterexample is a shortest trace. It checks every invariant in every state, reports a deadlock wherever no guard is enabled in a non-terminal state, and checks P ~> Q by decomposing the ¬Q subgraph into strongly connected components under weak fairness: a cycle only counts as a violation if no transition that leaves it stays enabled throughout. Liveness counterexamples are printed as lassos.

Execution

Proof-only constructs are erased before execution. The tree-walking interpreter, the bytecode VM and native binaries built through rustc share checked 64-bit arithmetic, Euclidean division, and limits of 64 nested calls and 100,000 loop steps; differential tests require identical output from all three. At run time, axioms are checked over the concept instances that actually exist (a closed world), while in the SMT encoding they hold over all models (an open world).

3Method

Each use case went through the same six steps.

  1. Draft the model from domain knowledge.
  2. Research and qualify sources. Every requirement, limit or physical constant is traced to a source and graded: A for standards, specifications and regulators; B for peer-reviewed work; C for manufacturer documents and patents; D for secondary sources used only to corroborate. Each entry also records how much of it was actually read. Several standards (ISO 10218, 13851, 13855 and 15622, and IEC 61511) are paywalled. Their figures come from secondary quotations and are marked as such.
  3. Encode each requirement as a contract, loop invariant, system invariant or temporal property, citing its key inline in the source file.
  4. Check with bil verify, bil model-check and all three back ends.
  5. Seed a bug. Each lesson gets a one-line variant in examples/domains/seeded_bugs/ that reproduces a documented failure mode. bil must reject it with a specific counterexample.
  6. Regress. tests/domain_examples.rs requires every model to be fully proved and every seeded bug to be caught. It runs in about nine seconds as part of the local CI gate.

The research corrected four first drafts. The SPE regrowth rates were low by about 15–20%; sensor plausibility used an arbitrary span instead of the NAMUR NE 43 failure bands; the ACC model used a "two-second rule" where the sources give standard minimum time gaps of 0.8–1 s and recommend 1–2 s; and the bank-angle protection forced a roll-back even while the pilot held the stick, which is not how normal law behaves. The model checker also corrected one draft: an MQTT model whose retransmission guard was too strict to expose the bug it was written to show.

Semiconductor manufacturing · lead case

Spectroscopic ellipsometry gating a solid-phase epitaxy anneal

25 obligations proved158 statesAnnealFinishes LTL proved2 seeded bugs caughtsemiconductor_se_spe.bil

Process context

Ion implantation amorphizes a surface layer of a silicon wafer. A thermal anneal then regrows it epitaxially from the crystalline substrate below: solid-phase epitaxy (SPE). Two measurements and one control loop decide whether the result is single-crystal silicon.

  • Metrology before the anneal. Spectroscopic ellipsometry measures the change in polarization, Ψ and Δ, over wavelength [[c:fujiwara2007]]. Fitting a multilayer optical model (oxide, amorphous layer, damaged substrate) gives the amorphous layer thickness. The fit has to be trusted with care: with an unsuitable dielectric-function model, ellipsometry can overestimate low-level damage [[c:lohner1996]]. SE has been used to follow the regrowth of implant-amorphized silicon [[c:holgado1995]].
  • Kinetics of the regrowth. For intrinsic Si the regrowth front moves at v = 4.64×10¹⁶ Å/s · exp(−2.7 eV / kT) [[c:roth1990,johnson2007]]. That is about 1.4 Å/s at 550 °C, 12 Å/s at 600 °C and 84 Å/s at 650 °C, so 30 °C of error changes the anneal time by a factor of two or more. Random nucleation in the amorphous layer has a higher activation energy, about 4 eV, so it gains on epitaxy as temperature rises [[c:olsonroth1988,olson1985]]. This sets the upper edge of the process window.
  • The thermal hazard. Amorphous Si melts 200 ± 50 K below crystalline Si. Under pulsed heating, a thin liquid layer can then propagate through the amorphous film at 10–20 m/s and leave fine-grained polycrystalline silicon: explosive crystallization [[c:thompson1984]]. In rapid thermal processing, temperature non-uniformity during ramps causes slip, which limits how fast the lamps may slew [[c:norman1991,uspto6403925]]. Typical RTP ramps run at 20–100 °C/s [[c:uspto6034356]].
  • In-situ monitoring. Real-time SE during solid-phase crystallization yields both a near-surface temperature calibration and the crystalline volume fraction over time [[c:fujiwara1998]]. This makes an ellipsometric endpoint for the regrowth, and a second temperature channel, practical.

What is modeled and proved

The SE gate accepts a site only when the regression converged, the fit error is under a threshold, and the thickness is inside the implant recipe's expected range. z3 proves the gate is exactly that predicate, with no hidden case:

[[x:examples/domains/semiconductor_se_spe.bil|fn se_site_valid|=&& s.a_si_thickness_a >= t_min && s.a_si_thickness_a <= t_max]]

The wafer disposition is proved for all inputs: fewer than 80% usable sites always sends the wafer back to metrology, and enough sites with a uniform layer always releases it. The regrowth-rate table comes from the Arrhenius law above. Each band uses the rate at its lower edge, so a time computed from it is never optimistic, and z3 proves the rate is zero outside the window and positive inside:

[[x:examples/domains/semiconductor_se_spe.bil|fn spe_rate|=fi]]

The fast thermal loop is where the hazards meet. Whatever the outer loop demands, the per-tick setpoint stays within the slew limit and never exceeds the hard temperature limit. All five branches are proved, including the case where the demand is above the hard limit while the current setpoint is below it:

[[x:examples/domains/semiconductor_se_spe.bil|fn thermal_setpoint|=fi]]

The anneal itself is a system with temperature in bands. Lamp drift or latent-heat release may push the wafer out of the window at any time during the soak, up to a bounded number of excursions, and the pyrometer may fail at any point. Five invariants are checked in all 158 reachable states, and AnnealFinishes proves under weak fairness that every anneal that starts ramping ends in Done or Reject:

[[x:examples/domains/semiconductor_se_spe.bil|invariant NeverMeltAmorphousSi|invariant OverTempIsTransient]]

On the example wafer W07 the verdict is [[run:examples/domains/semiconductor_se_spe.bil:verdict]]. Only three of five sites pass the SE gate, which is under 80%, even though the three good thicknesses are uniform (uniform = [[run:examples/domains/semiconductor_se_spe.bil:uniform]], mean [[run:examples/domains/semiconductor_se_spe.bil:mean_a]] Å). At 600 °C that layer needs [[run:examples/domains/semiconductor_se_spe.bil:ticks_600c]] one-second ticks to regrow, computed by regrowth_ticks, which is proved to terminate with the whole layer consumed.

What the checker found

A thermal loop one tick too slow melts the amorphous layer. If the controller can heat once more while already in the over-temperature band, the wafer reaches band 8, which is the a-Si melt and explosive-crystallization hazard. The checker returns the shortest path to it:

[[trace:spe_slow_thermal_loop.bil]]

An invariant that was too strong. The first draft stated that over-temperature can only occur during the soak. The checker showed a pyrometer fault in the middle of an excursion: the lamp is cut and the phase moves to Cool while the wafer is still in band 7. Cutting the lamp is the right response, so the invariant was corrected rather than the design.

[[trace:spe_overtemp_only_in_soak.bil]]

Limits. Temperature is discretized into bands and time into ticks. A production controller needs dense-time or hybrid analysis of the plant, and the window edge (680 °C here), the fit thresholds and the excursion budget are example recipe parameters, not recommendations. The model proves the supervisory logic and the per-tick command bounds, not the thermal physics.

Critical process systems

A safety instrumented system for an exothermic reactor

2 obligations proved23 statesTripIsReset LTL proved2 seeded bugs caught

The T2 Laboratories explosion was a runaway reaction after a cooling failure [[c:csb_t2]]. A safety instrumented system under IEC 61511 [[c:iec61511]] is the independent layer meant to stop that sequence. Three temperature transmitters voted 2-out-of-3 tolerate one fault both against failing to trip and against tripping spuriously [[c:lundteigen_sis]], at a higher cost and complexity than simpler architectures [[c:kenexis_2oo3]]. Both properties are proved for all inputs:

[[x:examples/domains/process_safety_reactor.bil|fn vote_2oo3|vote_2oo3(t1 >= setpoint]]

The reactor system lets cooling fail at any time. While running, the SIS trips at band 7 and pre-empts further heating, residual heat may add one more step, and the reactor is reset after cooling. The design temperature is never exceeded, and every trip is eventually reset.

What the checker found

If heating is not pre-empted at the trip point, which is what happens when the SIS responds more slowly than the reaction, the interleaving lets the temperature climb past the design limit before the trip fires:

[[trace:reactor_slow_sis.bil]]

Limits. Response time is abstracted as transition priority. Probability of failure on demand, proof-test intervals and common-cause failure, which IEC 61511 requires, are outside the model.

Collaborative robotics

Speed and separation monitoring in a cobot cell

8 obligations proved6 statesEStopIsReleasable LTL proved1 seeded bug caught

ISO/TS 15066 defines speed and separation monitoring (SSM) as one of four collaborative modes [[c:isots15066]]. NIST has published guidance on implementing its protective separation distance [[c:marvel2017]] and built a laser-scanner testbed that stops and restarts a robot from it [[c:szabo2012]]. The model takes the protective distance as an input and adds a 500 mm collaborative band capped at the 250 mm/s reduced speed associated with ISO 10218 [[c:iso10218]]:

[[x:examples/domains/robotics_cobot_cell.bil|fn ssm_speed_limit|=fi]]

The cell supervisor lets the human move between zones at any moment, with the scanner's safety output acting in the same step. Four invariants hold in every state: standstill in the protective zone, reduced speed in the shared band, E-stop means stop, and a valid zone.

What the checker found

The first draft claimed that a protective stop always clears. It cannot, because the human may stay in the protective zone, or press E-stop again, forever. The checker returns that as a fair lasso. What the controller can promise is that a latched E-stop is always releasable, and that is now proved.

[[trace:robotics_stop_always_clears.bil]]

Surgical robotics

Teleoperation with virtual fixtures and a link watchdog

9 obligations proved7 statesHoldIsLeftWhenLinkIsUp LTL proved

Virtual fixtures, introduced for telepresence by Rosenberg [[c:rosenberg1993]], include forbidden-region fixtures that keep a manipulator out of parts of the workspace. They have been studied on the da Vinci and JHU Steady-Hand platforms [[c:abbott2007]]. Robotically assisted surgical equipment falls under IEC 80601-2-77 [[c:iec80601277]]. The model proves three instrument-level functions: a depth fixture that never lets the tip pass the limit while leaving retraction unrestricted, 5:1 motion scaling, and a symmetric force limit.

[[x:examples/domains/surgical_teleoperation.bil|fn fixture_step|=fi]]

The supervisor puts the arm on hold when the console link drops. When the link returns, the arm stays on hold until the surgeon releases and re-presses the clutch. NoMotionWithoutReengage is checked in every state, because motion that resumes on its own when the link recovers is the hazard.

Medical devices

A patient-controlled analgesia infusion pump

9 obligations proved11 statesClearPumpCanRun LTL proved1 seeded bug caught

The FDA's Infusion Pump Improvement Initiative cites failures of built-in safety alarms among recurring defects [[c:fda_ipii]]. The FDA's Generic PCA pump model and its safety requirements have been model-checked in UPPAAL by others [[c:kim2011gpca,gpca_umn]]. This model proves the bolus rule (lockout interval and hourly cap, stated as an exact equivalence) and that delivery never exceeds the volume to be infused and stops exactly on it. The interlock system checks no free flow with the door open, a stop on occlusion or air-in-line, and an alarm that latches the motor off.

[[x:examples/domains/medical_infusion_pump.bil|fn infuse|=then v]]

What the checker found

"Every alarm is eventually cleared" does not hold. Hazards can keep recurring, and clearing an alarm is a clinical action rather than something the pump controls. The checker returns a fair lasso of alternating occlusion, air and door faults:

Manufacturing

Hydraulic press guarding and gravimetric dosing

10 obligations proved13 statesNoStuckDownstroke LTL proved

Two-hand control under ISO 13851 type III requires both actuators within 0.5 s, and both released before re-triggering [[c:iso13851]]. A light curtain must be mounted at least S = K·T + C from the hazard, with K = 2000 mm/s and C = 8(d − 14) for resolutions d ≤ 40 mm [[c:iso13855]]. Sources disagree on when K may drop to 1600 mm/s, so the model always uses the larger distance:

[[x:examples/domains/manufacturing_press_cell.bil|fn light_curtain_distance|=2 * t_stop_ms + 8 * (d_mm - 14)]]

The press system lets either hand release, the curtain break or the door open during the down-stroke, and the safety relay reverses the ram in the same step. DownstrokeIsGuarded holds in every state, and every down-stroke returns to the top. Coarse/fine dosing is proved never to overfill and to end exactly on target.

Industrial IoT

MQTT exactly-once delivery and NAMUR NE 43 telemetry

8 obligations proved21 states1 seeded bug caught

The model sends one QoS 2 PUBLISH over a network that may lose any packet, with timeout retransmission at the sender. MQTT 3.1.1 requires the receiver to acknowledge re-sent PUBLISHes until PUBREL and "MUST NOT cause duplicate messages to be delivered" [MQTT-4.3.3-2], and it assumes "an ordered, lossless, stream of bytes" underneath (§4.2) [[c:mqtt311]]. The sender side keeps its copy until PUBREC and the packet identifier until PUBCOMP [[c:emqx_qos]]. With an in-order transport, the model checker shows at most one delivery in every state and delivery whenever the sender reaches Done.

What the checker found

Drop the ordering assumption, so that PUBREL can overtake a retransmitted PUBLISH, and the receiver releases the packet identifier before the duplicate arrives. The duplicate is then delivered as new. The protocol's exactly-once guarantee depends on the transport, and the model makes that dependency explicit:

[[trace:mqtt_unordered_transport.bil]]

The same file classifies 4–20 mA loop currents under NAMUR NE 43: 3.8–20.5 mA is a measurement, and ≤ 3.6 mA or ≥ 21 mA signals a failure [[c:namur_ne43]]. The classification is proved for every input and drives a telemetry pipeline that flags [[run:examples/domains/iiot_mqtt_qos2.bil:failed]] as failed and [[run:examples/domains/iiot_mqtt_qos2.bil:suspect]] as suspect.

[[x:examples/domains/iiot_mqtt_qos2.bil|fn ne43_class|=fi]]

Automotive

Adaptive cruise control with an emergency-braking override

A review of ACC parameterization reports standard minimum selectable time gaps of 0.8 s and 1 s, and a recommended range of 1–2 s [[c:bernsteiner2016]]. Between α-prot and α-max the stick commands angle of attack, and α-max is never exceeded [[c:airbus_laws]]. Public safety

Signals with emergency preemption, a level crossing, and dispatch triage

1 obligation proved11 states in 2 systems3 LTL proved

A conflict monitor or malfunction management unit forces an intersection into flash when it sees conflicting greens [[c:mmu]]. The MUTCD requires a steady yellow after every green and leaves red clearance to engineering practice [[c:mutcd4d26]]. The intersection model proves no conflicting greens, the property the monitor enforces in hardware, in every state, including during emergency preemption. It also proves that preemption ends and that north–south traffic is served.

The level crossing follows Heitmeyer and Lynch's Generalized Railroad Crossing benchmark [[c:heitmeyer1994]]: the gate is down whenever the crossing is occupied, and it reopens once the train has gone. The siting assumption, that the gate is down before a train can arrive, is written as an explicit guard rather than hidden. Dispatch triage is a proved scoring function and a pipeline over an incident queue.

[[x:examples/domains/public_safety_traffic_rail.bil|system LevelCrossing|=}]]

Rate limiting, lockout, handshake ordering and separation of duties

6Cross-cutting lessons

  • Liveness often belongs to the environment. In the cobot cell and the infusion pump, the natural liveness claim ("the stop clears", "the alarm clears") was false, because a person or a recurring hazard controls it. The checker separates what the controller can guarantee from what it cannot, which is the distinction a hazard analysis needs.
  • Protocols carry hidden assumptions. MQTT's exactly-once guarantee is only as good as in-order transport. Writing the assumption as a guard means that deleting it produces a counterexample instead of silently weakening the proof.
  • Response time is a safety property. In the reactor and the SPE anneal, a protection function that was logically correct but one step slower than the hazard was unsafe. Interleaving semantics finds these races without a timing model, as long as the race is modeled as a choice.
  • Counterexamples also find over-strong requirements. The SPE invariant was wrong, not the design. A refuted property is a question to answer, and sometimes the answer is to fix the specification.
  • Formal models need primary sources. Four drafts changed after research, and in each case the model was internally consistent and verified before the correction. A proof shows that the model meets its specification. Only sources show that the specification matches the world.

7Limitations and threats to validity

  • Abstraction. Continuous quantities are integer bands and time is discrete steps. Claims are about supervisory logic and per-step bounds. Dense-time and hybrid properties need timed or hybrid automata.
  • SMT encoding. Calls to user-defined functions are unfolded into the SMT query, together with the callee's requires and ensures checks that execution performs on every call. Recursive calls, and calls inside a quantifier to a function that has a contract, are not unfolded, so those obligations are only bounded-checked.
  • Bounded cross-check cost. The bounded sampler that runs beside SMT enumerates the product of every parameter's sample domain. A function with a record and four integer parameters took 59 seconds to verify in a debug build, so the navigation model passes records instead. A sample cap is on the roadmap.
  • Arithmetic. SMT reasons over unbounded integers, while execution uses checked 64-bit integers that stop on overflow. Proofs therefore cover the intended mathematics, and execution fails loudly outside it.
  • Sources. Several standards were read only through secondary quotations, and those figures are marked in the citations. Parameters in the models are illustrative, not compliance values.
  • Assurance. bil is not a qualified tool under IEC 61508, ISO 26262, IEC 62304 or DO-330, and these models have not been reviewed by domain safety assessors. They demonstrate method, not certification evidence.

8Roadmap

  • Use proved callee contracts in place of unfolding, so recursive functions can be proved modularly.
  • Cap and randomize the bounded cross-check, with the sample budget reported.
  • Clocks and timed guards in system blocks, for response-time properties that are currently encoded as priority.
  • A refinement path from banded models to continuous controllers, ending in Verus-checked Rust through bil emit-verus.
  • Tool-qualification evidence: requirements tracing, coverage and independent test suites for the verifier itself.
